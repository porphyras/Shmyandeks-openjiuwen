# Независимый аудит: проверка coding-задач

База сравнения: `e15aeea` (main на 08.11.2026). Изменения ограничены запуском
тестов и одним правилом бесплатного отказа. Модели, промпты, бюджетный планировщик
и математический/табличный/поисковый fast path не менялись.

## 1. Ложное «тесты проходят»

Пример видимого теста без точки входа:

```python
import unittest
import mylib

class TestTotal(unittest.TestCase):
    def test_total(self):
        self.assertEqual(mylib.total([1, 2]), 3)
```

При `def total(xs): return 0` прежний `_run_tests` возвращал
`(True, 'Ran 0 tests\n')`: запуск файла только определял класс, а запасной
runner искал лишь функции в модуле. Из-за `initial_pass=True` задача могла
получить `DONE` до исправления исходника.

Теперь запасной runner загружает `TestCase` через `unittest.TestLoader`,
добавляет обычные синхронные функции в ту же suite и проверяет её результат.
Пустой список файлов и ноль выполненных тестов не означают успех. Убран
срез `tests[:5]`; общий срок выполнения сохранён и повторно проверяется перед
запасным запуском. Сырые async-функции без async-runner дают явную ошибку,
а не успех из-за невыполненного coroutine.

Прежний запуск файлов с `unittest.main()` сохранён. Запасной runner не реализует
pytest fixtures/parametrize и не засчитывает скрипты без обнаруженной тестовой
suite как пройденные. Поддержка этих форматов — отдельная задача.

## 2. Ложное «задача невыполнима»

Прежняя эвристика считала перестановки аргументов равнозначными по словам
`maximum`, `total`, `count` и т. п. в имени функции. Три обычных контрпримера:

| Функция | Вход → ответ | Перестановка → ответ |
|---|---|---|
| `maximum_profit` (купить раньше, продать позже) | `[1, 2, 3] → 2` | `[3, 2, 1] → 0` |
| `total_distance` (длина пути по точкам на прямой) | `[0, 1, 3] → 3` | `[0, 3, 1] → 5` |
| `count_switches` (число смен соседнего значения) | `[0, 1, 0] → 2` | `[0, 0, 1] → 1` |

Все три получали бесплатный отказ даже при корректной реализации. Правило
удалено: название не доказывает независимость от порядка. Проверки одинаковых
вызовов с несовместимыми требованиями, return/raise и остальные детекторы сохранены.

Компромисс: действительно невозможные задачи, которые обнаруживались только
этой эвристикой, теперь могут расходовать токены. Изменение устраняет конкретные
ложные отказы; прирост итогового балла и расхода токенов на реальном наборе не измерен.

## Проверка

- `python3 -m unittest discover -s tests -v`: 27 тестов проходят на Python 3.11.17
  и 3.12.15 (macOS).
  Новые случаи воспроизводили ошибки до исправления.
- Включён проход `prepare → solve → реальные тесты` для сломанной
  `maximum_profit`: заглушка модели возвращает правильную функцию, харнесс
  сохраняет исправление и выдаёт `DONE`. Сетевая модель не используется.
- Сгенерировано 100 задач: `python3 bench/gen_tasks.py --out bench/sets/up1ng-audit
  --n 100 --seed 20261108 --infeasible 0.2`. Сравнение `prepare` до/после не
  изменило наличие бесплатных отказов; на 80 выполнимых задачах их нет.
  Все 25 исходных coding-задач распознаны как не проходящие тесты обеими версиями.
- На этих 100 задачах проверены 59 бесплатных ответов и 9 бесплатных отказов:
  ошибок относительно ключей генератора нет. Это проверка регрессии на генераторе,
  не независимый прогноз качества на скрытом наборе соревнования.
- В отдельных временных workspace установлены эталонные реализации всех
  25 coding-задач: 20 выполнимых проходят видимые и скрытые тесты, 5 невыполнимых
  продолжают падать. Скрытые тесты есть у 20 выполнимых задач.
- `git diff --check` проходит. Реальный API не вызывался. Docker-прогон не
  выполнялся: локальный Docker daemon недоступен.

Перед слиянием полезен штатный прогон команды в контейнере на её закрытых наборах.
