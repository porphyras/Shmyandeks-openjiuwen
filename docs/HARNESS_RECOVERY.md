# Два исправления оболочки: очередь и повторный поиск

Основа: main `e15aeea`. Изменяются собственные `Run` и `Solver`, без замены
openJiuwen-клиента, моделей или формулы учёта токенов.

## Резерв не равен расходу

Контролируемый сценарий: 6 задач, 3 рабочих потока, бюджет 200, прогноз каждой
задачи 100, фактический расход после завершения 1. Первые две задачи ждут события
давления на бюджет. Третий поток обнаруживает нехватку свободного резерва.
Событие освобождает первые две задачи; временных sleep в тесте нет.

До исправления оставшиеся задачи удалялись из heap. В воспроизведении решены
2 из 6, расход 2, остаток 198 — задачи сами по себе были доступны.

Теперь задача откладывается, если её прогноз помещается в фактический остаток,
но не помещается рядом с резервами активных задач (`defer_budget`). После
завершения текущей волны исходные записи возвращаются в heap, сохраняя приоритет
и уровень повторной попытки. Задача, которая не помещается даже в фактический
остаток, по-прежнему пропускается (`skip_budget`). В том же сценарии решены
6 из 6, расход 6.

После join всех потоков резерв точно обнуляется, чтобы погрешность float не
создавала бесконечных волн. Перед новой волной проверяются STOP, исчерпание
квоты и остаток времени. Отложенные задачи повторно проходят прежнюю проверку
доступности бюджета. Это исправление очереди, не гарантия жёсткой верхней границы
расхода: резерв по-прежнему строится на прогнозе.

Цена изменения: дополнительные волны могут увеличить число запусков worker pool
и число попыток решения по сравнению с прежним преждевременным пропуском. При
большом свободном бюджете отложенной очереди нет. Выигрыш на настоящем наборе
с бюджетом 100k не измерен; 2/6 → 6/6 — результат управляемого сценария.

## Новый контекст может быть короче

После `NOT FOUND` запасной фрагмент базы раньше использовался только если был
длиннее первого более чем на 10 символов. Это отбрасывало новые факты из более
короткого или равного по длине фрагмента и давало ложный отказ.

Теперь непустой фрагмент, отличающийся от предыдущего, допускается ко второй
попытке. В тесте первый контекст не содержит ответа, второй содержит связь
`Alice Wang → Cobalt Works → Graz`. До исправления — один запрос и `infeasible`,
после — два запроса и проверенный по тексту ответ `Graz`.

Пустой или идентичный фрагмент не вызывает повторный запрос; успешный первый
ответ не вызывает повторное извлечение. Прежний предел четырёх попыток сохранён.
Отличающийся текст не гарантирует новых полезных фактов, поэтому изменение
может добавить запрос и без прироста балла. Нужен A/B-прогон на закрытых наборах.

## Проверки

```bash
python3 -m unittest discover -s tests -v
```

Добавлены 9 тестовых методов. Проверяются оба исправления, реальная нехватка
бюджета после дорогих завершений, остановка по квоте, float-остаток,
сохранение уровня второго прохода, короткий/равный/слегка более длинный контекст
и отсутствие лишних запросов при прежнем тексте или готовом ответе.

Регрессии используют контролируемые solver/ledger/LLM-заглушки. Очередь Run и
записи результатов настоящие; качество прогнозов, HTTP, SDK и реальный биллинг
этими тестами не проверяются. Реальный API не использовался.

Полный набор этой ветки: 24 теста проходят на Python 3.11.17 и 3.12.15 (macOS).
Во временном worktree проверено объединение с PR #2 и #3: 47 тестов проходят
на Python 3.12, отрицательные контроли из PR #3 обнаруживают 9/9 ошибок.
